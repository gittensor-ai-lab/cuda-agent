Compute Serving ​

Gittensor's second competition pays miners for serving verified inference. A compute miner runs one blessed model on one blessed runtime on an RTX 5090; validators prove the card is real and holding the model, route real traffic to it, verify the answers against their own copy of the model, and pay per output token served — at a rate set so that one 5090 flat out for an hour earns the posted card-hour — out of a capped serving pool.

This page is the mechanism: how verification, scoring, settlement, pay and the caller gate work, and what changes with notice. To set up a card, follow the Compute Miner Guide. Validators enable serving in the Validator Guide.

INFO

Serving is paid per output token served, priced so that a 5090 flat out earns $0.70 per card-hour (≈ $0.69 per million output tokens on the current runtime), capped at 5 % of emissions (SERVING_EMISSION_SHARE_CAP); 90 % is the OSS Contributions pool (OSS_EMISSION_SHARE), and the remaining 5 % is reserved for neither pool — it recycles to UID 0 every round. A hotkey can earn from both at once — serving rewards and repository rewards are summed per UID.

1. What you run ​

Modelqwen3.6-35b-a3b — Qwen3.6-35B-A3B UD-Q4_K_M (~22 GB, fits one RTX 5090)
Runtimesparkinfer_server at the pinned commit named on the Current release card, shipped as the Docker image entrius/sparkinfer:<runtime_tag>
Model filepinned by model_sha256 in the same file — the runtime verifies the digest on start
DeterminismSPARKINFER_DETERMINISTIC=1 (baked into the image) — bit-reproducible greedy decode is what makes verification exact
Attest containerentrius/gt-attest:<attest_tag> — one per hotkey, beside the runtime, on that hotkey's GPU(s). Answers the validators' hardware challenge (§3.4) — pass/fail admission, nothing counts cards. Runtime-agnostic: the same image serves every blessed release
Neuronneurons/serving_miner.py — a thin proxy between the Bittensor axon, the runtime and the attest container; run it unmodified

Where the current values come from

The one canonical source for the current release — model id, runtime pin, runtime image, attest image, model sha256 and the copy-paste docker run lines — is the "Current release" card on gittensor.io/compute. Images for every blessed runtime/model are published under the entrius org on Docker Hub; the release card names the one to pull. Never copy a pin from a doc page — a pin bump would strand it.

The image tag is the release. Validators verify against their own honest copy of the exact same image, so any other build, quantisation or runtime fails verification. The interface a runtime has to satisfy is the Serving Runtime Contract; a second model or runtime is added by blessing another release — it appears on the release card and validators enforce it from their release list.

Miners run inbound axons: the validator's dendrite calls you, so you need a public IP and one open TCP port. Miners are expected to be co-located with their GPU — proxying to a GPU in another region costs speed credit and so traffic (§3.2), and one GPU behind several hotkeys only splits that one card's tokens between them (§3.4).

2. How validators verify you ​

There are no synthetic audit prompts. The requests a validator's gateway routes to you are the audit:

  1. A user (or the validator's own baseline traffic, §2.2) sends an OpenAI chat completion to the validator's gateway. The gateway dispatches it to a READY miner — the one with the fewest requests in flight — and streams your answer back.
  2. Your runtime decodes greedily (temperature 0) with per-token logprobs and token ids, streamed as chat.completion.chunk events. The neuron forwards the stream untouched.
  3. On the validator's next audit round (every 5 minutes, on its own clock) it teacher-forces your completion under its reference — a live copy of the release on a GPU the validator controls, via the runtime's POST /v1/score (contract R8). Your token ids are fed in; the reference reports its own argmax and logprob at every position. One prefill pass, no generation.
  4. The verdict is decisive per request. The blessed runtime is bit-reproducible, so an honest miner matches exactly: every token equals the reference argmax, mean |Δlogprob| ≤ 0.005, max |Δlogprob| ≤ 0.10. Every planted cheater tested (other runtimes, other quantisations) differs on every prompt.

Verification is one reference prefill per request, so it is sampled: each round, per hotkey, every baseline prompt and every failed request is verified, plus a random max(10, 20 %) of your completed gateway requests (SERVING_AUDIT_SAMPLE_MIN, SERVING_AUDIT_SAMPLE_FRACTION). A low-traffic miner is verified in full; a busy one is verified on a draw it cannot predict. Because verification rides on real traffic, there is nothing on the wire a miner can tell apart from unaudited traffic, and nothing to memorise.

2.1 The window ​

Each verdict enters a rolling window of your last 10 verified requests per (hotkey, release):

OutcomeWhat enters the window
Pass1
Miss — no answer within 30 s, stream ended without [DONE], empty completion, wrong model, or a completion that re-tokenises to a different length0
Wrong answer — tokens or logprobs outside the bands with aligned lengthsnot a miss: the window is wiped and the hotkey is quarantined for 1 hour (SERVING_QUARANTINE_S). There is no honest way to produce one on the blessed pin.

You are READY while the window mean is ≥ 0.8 over at least one verified request (SERVING_AUDIT_WINDOW_THRESHOLDS). With a deterministic runtime the honest mean is 1.0, so the bar only leaves room for transient misses: three misses in your last ten requests drop you; passing traffic brings you back. The window is keyed by hotkey and persisted on the validator, so a validator restart does not reset it and a UID that changes hands starts empty.

2.2 Probation and baseline traffic ​

A miner that is not READY (and not quarantined) sits in probation. User traffic never reaches probation miners. Instead, every audit round the validator itself sends every serving axon 2 baseline prompts (SERVING_BASELINE_PER_ROUND), at random moments spread over the round, through the same path as user traffic. Baseline requests are verified like anything else, so:

  • a brand-new miner earns a window and reaches READY with zero users — typically on the second audit round after it comes up;
  • a validator with no API users can still verify and pay the whole fleet;
  • quiet hours are never a free period — the baseline keeps proving you are up and correct.

Real traffic adds to the baseline; it never displaces it.

3. How you are scored ​

Per validator, per 5-minute round:

admitted     = window_pass × (speed_credit > 0) × attested                    (§2.1, §3.2, §3.4)
round_score  = admitted × output_tokens_served ÷ (aggregate_decode_tps × round_seconds)

output_tokens_served is what the validator's gateway saw you stream on user traffic this round — counted by the gateway as it relays your stream, never reported by you, and never more than the request asked for. Baseline prompts (§2.2) are verified like everything else but pay nothing: they anchor eligibility, not income. aggregate_decode_tps is the blessed release's measured output throughput for one card under load (speed.aggregate_decode_tps in the release list; ~280 tok/s on the current runtime), so a round score of 1.0 is one card flat out for the round — ~84k output tokens in five minutes, ~1M in an hour.

There is no card count and no per-hotkey cap. A real 5090 cannot out-decode its silicon, so served volume is the capacity proof: 1.5M correct tokens in an hour is paid as 1.5 card-hours, whatever hardware attested behind it, and an idle card is paid nothing however real it is.

3.1 Correctness ​

Decided by the window (§2.1). A round in which you are not READY scores 0, including every token you served in it. Verification is sampled: an unsampled completion is paid in full while your window passes, a sampled one is paid only if it verified, and a wrong answer wipes the window and quarantines you — the hour of quarantine is an hour of unpaid serving, on top of the traffic you stop receiving the moment you leave the READY set.

3.2 Speed — routing weight ​

Speed is measured on the traffic you actually served, per verified request:

  • Time to first token — the validator's own clock from dispatch to the first streamed event (network + queue + prefill). Full credit up to 500 ms, falling linearly to zero at 1500 ms (SERVING_LATENCY_FULL_CREDIT_MS, SERVING_LATENCY_ZERO_CREDIT_MS). An honest 5090 answers the first token in tens of milliseconds on-box; add the round trip and an honest miner anywhere on earth lands well inside full credit.
  • Decode rate — completion tokens per second after the first token, on requests of 32+ tokens (SERVING_DECODE_MIN_TOKENS), against the blessed release's measured per-request curve at the load this validator had in flight to you (speed.decode_per_request in the release list; ~440 tok/s alone, ~19 tok/s each at 16 concurrent). Full credit down to 0.8× the curve, linear to zero at 0.5× (SERVING_DECODE_TOLERANCE_RATIO, SERVING_DECODE_FLOOR_RATIO).

Speed credit is your routing weight, not a pay multiplier. The gateway sends each request to the READY miner with the fewest requests in flight, choosing among ties at random weighted by credit — so a remote, queued or shared card is sent less and serves fewer paid tokens, and under 0.5× the curve (credit 0) you are not READY at all. With no user traffic the credit is measured on the baseline prompts.

3.3 Settlement ​

Round scores are settled over the trailing 12 rounds (one hour, SERVING_SETTLEMENT_ROUNDS): your settled score is the mean of your last 12 round scores, with missing rounds counting 0 — that is, the hour's served tokens in card-hours. A card that served ~1M output tokens over the last hour settles at ~1.0; one that was READY but routed nothing settles at 0. The OSS scoring round picks up the latest settled serving scores when it blends emissions.

3.4 Admission — hardware attestation ​

Attestation answers one question: is there a real 5090 running the real model behind this hotkey? It gates entry to the READY set; it does not price anything. Each round the validator draws a cohort — half the READY miners, least recently challenged first, plus every miner that has never passed or failed last round (SERVING_ATTEST_COHORT_FRACTION) — and sends them one fresh random seed. Your attest container runs gt_attest on every GPU it can see: it fills the card's free VRAM with a seeded stream and runs a deterministic fp32 GEMM chain over it, and returns per card the GPU UUID, bytes filled, a SHA-256 digest of the chain and the wall time. The validator has asked its own reference card the same seed first, so it knows the expected digest and an honest wall time.

A card passes when:

  • the digest matches — only a real sm_120 card running the chain produces it;
  • the wall time is within 1.6× the reference's (SERVING_ATTEST_BUDGET_RATIO), and the whole reply arrived within that budget plus 2 s of network slack — the container runs challenges one at a time and counts the queue wait in the wall, so a challenge queued behind another hotkey's on a shared attest container runs ~2× slower and fails — one attest container per hotkey;
  • at least 60 % of the free VRAM was filled (SERVING_ATTEST_MIN_FILL_RATIO);
  • the model was resident before the fill: free VRAM at most total minus 0.8× the release's reservation (SERVING_ATTEST_MODEL_RESIDENT_RATIO) — a bare card with nothing loaded is not a serving card.

You are attested when any card you report passes; the per-card verdicts and UUIDs are telemetry, not pay. A failed attestation is never a strike — you are not READY that round (its tokens go unpaid) and are challenged again next round; miners not drawn keep their last verdict for up to 12 rounds (SERVING_ATTEST_MEMORY_ROUNDS). A miner with no verdict yet is not READY, so a new card is attested before it sees user traffic.

What this makes pointless: claiming cards you do not have (the count pays nothing), several hotkeys on one card (they split one card's tokens and each looks slow under load), a card attested here and traffic served from elsewhere (the model must be resident on the attested card, and served speed decides your routing), and an idle second card (nothing served, nothing paid). One hotkey per card is the simple setup — a box with N cards runs N hotkeys.

4. Pay ​

Serving miners are paid per output token served, at a rate derived from one hand-set number:

token_rate      = $0.70 per card-hour  ÷  (aggregate_decode_tps × 3600)      (≈ $0.69 per million output tokens today)
card_hours_i    = settled_score_i                                            (served tokens ÷ what one card decodes in an hour)
target_share    = Σ card_hours_i × $0.70  ÷  (alpha/h to miners × alpha_TAO_price × tao_usd)
serving_share   = min(target_share, 0.10)
reward_i        = serving_share × card_hours_i / Σ card_hours
  • $0.70 is SERVING_GPU_HOUR_USD, the only hand-set price: what a 5090 flat out for an hour earns. The per-token rate follows from the release's measured throughput, so each blessed release prices itself, and a faster runtime lowers the price per token rather than the price per card-hour. The alpha/TAO price is read on-chain; the TAO/USD rate is published with the release in the validators' release list (shown on the /compute page). Both inputs are ones every validator observes identically, so validators agree on the share.
  • The only ceiling is the emission pool. The share is capped at 5 % of emissions (SERVING_EMISSION_SHARE_CAP). Below the cap every token is paid at the full rate — there is no per-hotkey cap, so a hotkey that served 1.5 card-hours of tokens earns 1.5 × $0.70. Above the cap the pool is split pro-rata by token share: more demand fills more cards, it never pushes a card above the posted rate.
  • What the fleet does not earn recycles to UID 0, never to OSS. With no price data (testnet) the whole cap is paid pro-rata.
  • Per-validator scores are blended into on-chain weights the same way as OSS scores. A validator that has no reference GPU cannot verify anything and sends its serving cap to UID 0 (see the Validator Guide).

The price, the cap and the OSS/serving split are validator-code constants and will be revised with notice — changes are announced in Discord before they land on main. Pay follows traffic, so early income is lumpy round to round; the hour's settlement smooths it, and the gateway's spread (§3.2) is what decides who serves.

5. Who may query a miner — the caller gate ​

A miner's axon answers only:

CallerLimit
Any hotkey with ≥ 1,000,000 alpha staked on the subnet (SERVING_MIN_CALLER_STAKE)unlimited — this is the gateway-running validator
Any hotkey holding a validator permitany request shape, up to 50,000 completion tokens per tempo per miner (SERVING_VALIDATOR_TOKENS_PER_TEMPO) — enough to run an independent reference and verify a fleet of ~100 miners several times over, worthless as free inference
Anyone elserefused (Stake N below 1000000)

Everyone else goes through a validator's gateway (POST /v1/chat/completions on port 8790 behind API keys), which only ever routes user keys to READY miners and answers 429 when there is no READY capacity rather than queueing. Requests are standard OpenAI chat completions — stream: true is supported, logprobs: true returns per-token logprobs, max_tokens is capped at 1024, n must be 1, message content must be plain strings. Sampling parameters are ignored: every answer is a greedy decode, which is what makes it verifiable.

bash
curl http://<validator>:8790/v1/chat/completions \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"qwen3.6-35b-a3b","messages":[{"role":"user","content":"hello"}],"stream":true}'

Each response carries gittensor.served_uid so you can see which miner answered.

6. How to read your status ​

The /compute page on gittensor.io shows the serving fleet: per-UID status (ready / probation / quarantined), window mean, speed credit, observed TTFT and decode rate, attestation, settled score (card-hours of served tokens) and the current serving share. A validator's GET /v1/serving/status (with a gateway key) exposes the same round report, including the output tokens paid this round and the per-card attestation verdicts.

Read the numbers there with two caveats:

  • They are a snapshot from a single validator's audit loop. Every validator runs its own reference, its own baseline traffic and its own attestation cohorts on its own clock, and on-chain incentive is the stake-weighted blend across all of them. Another validator may see you differently (different RTT, different draw).
  • The pay figures are estimates: they apply the published TAO/USD rate and the on-chain alpha price at the time of the snapshot to that validator's settled scores. What you actually receive is set at weight-setting time.

7. Phase-0 limits ​

  • One runtime instance per card. The blessed model fits one 5090 and the runtime is single-card, so a multi-GPU box runs one runtime container per GPU behind one address (a small round-robin proxy) and one neuron; the attest container covers all of them. The neuron does not yet route across instances itself.
  • One release. One blessed release (the one on the Current release card), RTX 5090 only (the runtime promises reproducibility on the same GPU model only).
  • Inbound axons. Residential NAT needs a port forward; an outbound-only connector is on the backlog.
  • Pay follows traffic. A READY card with nothing routed to it earns nothing that round; with little demand the gateway's spread decides who serves, so income is lumpy until the fleet is busy. The free-tier launch traffic is what fills cards.
